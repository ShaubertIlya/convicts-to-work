# Архитектура платформы

## Принятый подход

Система реализована как модульный монолит. Это даёт одну транзакционную границу для
заявки, обследований и договоров, но сохраняет чёткое разделение предметных модулей.
Когда нагрузка или организационная структура потребуют разделения, границы модулей уже
подготовлены для выделения сервисов.

| Слой | Технология | Назначение |
|---|---|---|
| Web UI | Next.js, React, TypeScript | Лендинг, регистрация и ролевые кабинеты |
| API | Django, Django REST Framework | Авторизация, валидация и бизнес-процессы |
| Фоновые задачи | Celery, Redis | Основа для будущих уведомлений и генерации документов |
| Данные | PostgreSQL | Транзакционные данные и журнал действий |
| Файлы | S3 API / SeaweedFS | Эталонные фото и будущие PDF-договоры |
| Биометрия | Внешний `biometry-service` | Сверка лица, liveness и одноразовый `consume` |

Время хранится в UTC, а пользовательское представление работает в зоне
`Asia/Almaty`. Авторизация API построена на серверном DRF-токене, который передаётся
только через защищённую HttpOnly cookie. JavaScript не имеет доступа к токену, а для
изменяющих запросов дополнительно применяется CSRF-защита; JWT в браузере не используется.

## Модули backend

- `accounts` — пользователи, роли, регистрация МСБ и администрирование доступа;
- `organizations` — реестр МСБ, единая организация Еңбек, карточки организаций и справочник ОКЭД;
- `prisoners` — реестр, полные личные дела, навыки, рейтинг, фото и история изменений;
- `applications` — заявка, предложения кандидатов и два обследования;
- `contracts` — договор, подписи и попытки биометрии;
- `notifications` — внутренние уведомления;
- `audit` — неизменяемые прикладным API события значимых действий.

## Основные связи данных

```text
Organization ──< User
      │
      └──< JobApplication >── Skill
                 │
                 └──< CandidateProposal
                            ├── Prisoner
                            │      ├──< PrisonerSkill >── Skill
                            │      └──< PrisonerChangeHistory
                            ├──< Screening (MEDICAL, PSYCHOLOGICAL)
                            └── EmploymentContract ──< ContractSignature
                                           └──< BiometricSignatureAttempt
```

Карточка осуждённого не доступна МСБ. В предложении МСБ получает только фото, навыки
и рейтинг. ФИО и ИИН появляются у МСБ только внутри созданного договора, что соответствует
согласованным требованиям.

Сотрудникам Еңбек доступен отдельный реестр осуждённых с поиском и фильтрацией по
навыкам, образованию, квалификации, опыту, здоровью, инвалидности, ограничениям и
занятости. Из реестра открывается полное личное дело, включая сведения о наказании,
трудовом опыте, инструктажах и историю изменений квалификации, здоровья и занятости.

В момент отправки заявки в ней сохраняется снимок реквизитов организации: БИН, адреса,
ОКЭД с двуязычными названиями, банк, БИК, КБЕ, ИИК и данные руководителя. При создании
договора этот снимок фиксируется повторно и включается в digest документа. Поэтому
последующее редактирование карточки организации не меняет юридически значимые данные уже
созданной заявки или договора. Для старых записей без снимка API временно возвращает
актуальную карточку организации, что обеспечивает обратную совместимость миграции.

## Состояния процесса

Заявка проходит путь:

```text
DRAFT → SUBMITTED → PROPOSED → BUSINESS_RESPONDED → APPROVED
                                                     ↓
                                                 SCREENING
                                                     ↓
                                                CONTRACTING
```

Из процесса возможны явные выходы `WITHDRAWN`, `REJECTED_BUSINESS` и
`REJECTED_ENBEK`. Изменение заявки блокируется после первого ответа Еңбек.

Кандидат проходит состояния отдельно. Психологическое обследование нельзя назначить
до положительного медицинского заключения. Создать договор можно только для кандидата
в состоянии `READY_FOR_CONTRACT`.

Договор создаётся из заявки с её сохранённым снимком реквизитов. До подписания
сотрудник Еңбек прикладывает PDF; система проверяет формат и страницы, фиксирует
SHA-256 и не позволяет менять файл после первой подписи. Осуждённый знакомится с
этим PDF на месте, сотрудник подтверждает факт ознакомления перед запуском биометрии.
После биометрической подписи руководитель Еңбек и администратор МСБ могут подтвердить
договор кнопками в любом порядке. Статус `ACTIVE` устанавливается только при наличии
трёх подписей. Заявка получает `COMPLETED` только когда все её согласованные кандидаты
завершили маршрут и все созданные договоры подписаны.

## Граница биометрии

Исходный проект `biometry-service` не включён в этот репозиторий и не изменяется.
Интеграция использует опубликованный HTTP-контракт:

1. Backend генерирует криптографически случайный `state`, хранит только SHA-256 digest
   и отправляет эталонное фото по server-to-server каналу в `/verification/start`.
2. В попытке фиксируются договор, версия и digest его существенных полей.
3. Браузер переходит на штатный интерфейс биометрии.
4. Callback сверяется одновременно по `state` и `verification_id`.
5. Успешный callback сам по себе не является подписью. Backend обязательно вызывает
   одноразовый `/consume` и принимает только `verified=true`, `status=CONSUMED`.
6. Повторное использование попытки блокируется уникальными ограничениями и состоянием.

Локальный `BIOMETRY_CALLBACK_URL` задаётся **при запуске внешнего biometry-service**:

```text
http://localhost:3000/biometry/callback
```

Biometry Service не принимает callback в `/verification/start`, поэтому переменная с
таким именем в окружении Еңбек не настраивает возврат из внешнего сервиса. После
смены значения внешний сервис необходимо перезапустить; уже запущенные попытки
имеют короткий срок жизни и должны быть начаты заново. Callback через порт 3000
обрабатывается маршрутом Еңбек и передаётся во внутренний backend. Затем backend
сверяет `state` и `verification_id`,
вызывает одноразовый `/consume` и только после подтверждения записывает подпись
осуждённого. При отказе или истечении срока подпись не создаётся; браузер всегда
возвращается на `/contracts` с результатом операции. Для других рабочих станций
вместо `localhost` потребуется доступный им внешний адрес Еңбек.

Кадры камеры и видео платформа не сохраняет: текущий биометрический сервис их не
возвращает. Доказательством в первой версии служат идентификатор успешно потреблённой
проверки, время, инициатор, версия и digest договора. Liveness текущего внешнего сервиса
не следует считать сертифицированной защитой от спуфинга без отдельной аттестации.

## Изоляция инфраструктуры

Compose-проект имеет фиксированное имя `convicts_to_work`. Все сети, контейнеры и тома
создаются только в этом namespace. PostgreSQL использует отдельные БД и пользователя
`convicts_to_work`, S3-хранилище — отдельный bucket `convicts-to-work`. В конфигурации нет
команд удаления БД, bucket или внешних Docker-ресурсов.

## Отложено до согласованного этапа

- утверждённый двуязычный шаблон и автоматическая генерация PDF (пока PDF загружается вручную);
- ЭЦП;
- восстановление пароля, email и SMS;
- сертифицированная антиспуфинг-проверка;
- историческая миграция данных и интеграционные шлюзы ЕТС;
- CI/CD и production topology.
