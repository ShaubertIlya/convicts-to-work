# Convicts service

## Текущий статус реализации

Реализован первый рабочий вертикальный срез системы:

- backend на Django 5.2 и Django REST Framework;
- frontend на Next.js 16 с русским и казахским лендингом;
- регистрация МСБ и токенная авторизация через защищённую HttpOnly-cookie;
- роли Еңбек и управление пользователями администратором;
- реестр и полные личные дела осуждённых, навыки, рейтинг и безопасная публичная статистика;
- реестр зарегистрированных организаций МСБ с полной карточкой и показателями активности;
- администрирование пользователей платформы, ролей и блокировки учётных записей;
- история изменений квалификации, здоровья и трудовой занятости осуждённых;
- заявки, отдельная страница подбора кандидатов и все согласования;
- медицинское и психологическое обследования в заданном порядке;
- договоры, биометрическая подпись осуждённого и кнопочные подписи сторон;
- отдельные табличные разделы заявок и договоров с поиском и фильтрацией;
- компактный адаптивный кабинет в светлом Material-стиле;
- внутренние уведомления и журнал значимых действий;
- PostgreSQL, Redis и MinIO в изолированном Docker Compose проекте.

Регистрация МСБ разбита на отдельные смысловые блоки. БИН и ИИН принимают ровно
12 цифр, телефон форматируется по маске, адреса можно синхронизировать флажком,
а банковские реквизиты проверяются как связка банка, БИК, КБЕ и ИИК. ОКЭД и банки
выбираются из загружаемых справочников; ИИК дополнительно проходит контрольную
проверку и сверку кода выбранного банка.

Реестры заявок и договоров показывают по 10 записей на странице, используют пагинацию
и занимают доступную высоту кабинета без внутренней вертикальной прокрутки. Черновик
заявки можно редактировать до отправки. Подбор осуждённых сотрудником Еңбек вынесен на
отдельную страницу заявки с поиском, подробными фильтрами и карточками кандидатов.

При отправке заявки и создании договора реквизиты организации сохраняются отдельным
снимком. ОКЭД, банк, БИК, КБЕ, ИИК, адреса и данные руководителя в уже созданных записях
не изменятся после редактирования профиля компании и участвуют в контроле целостности
договора.

Генерация двуязычного PDF по шаблону намеренно оставлена на последний этап, как было
согласовано. Поля документа и связь с заявкой уже предусмотрены в модели договора.
До утверждения шаблона сотрудник Еңбек может загрузить подготовленный PDF в карточку
договора. Без PDF и подтверждения ознакомления осуждённого биометрическую подпись
начать нельзя; файл фиксируется SHA-256, после первой подписи замена запрещена.

### Быстрый запуск через Docker

```bash
cp .env.example .env
docker compose up --build -d
docker compose exec backend python manage.py seed_demo
```

При старте backend автоматически применяет миграции и идемпотентно загружает
справочники ОКЭД и банков. Повторно это можно выполнить командой:

```bash
docker compose exec backend python manage.py load_reference_data
```

После запуска:

- сайт: `http://localhost:3000`;
- кабинет: `http://localhost:3000/dashboard`;
- заявки: `http://localhost:3000/applications`;
- договоры: `http://localhost:3000/contracts`;
- реестр осуждённых: `http://localhost:3000/prisoners`;
- организации МСБ: `http://localhost:3000/businesses`;
- администрирование: `http://localhost:3000/administration`;
- API: `http://localhost:8000/api/`;
- администрирование Django: `http://localhost:8000/admin/`;
- S3 API (SeaweedFS): `http://localhost:9000`.

Тестовые пользователи Еңбек создаются командой `seed_demo`. Пароль по умолчанию:
`Dev-password-123`; его можно заменить параметром `--password`. Все карточки этой команды
вымышлены: команда создаёт 20 кандидатов с разными навыками и по три записи истории
изменений для каждого. Для демонстрационного окружения используются тестовые портреты
из локальной папки `media/prisoners/reference/`; команда не скачивает фотографии из
интернета. Если локального портрета нет, создаётся нейтральная графическая заглушка.
Демонстрационные портреты не соответствуют ФИО карточек и не подходят для проверки
биометрии реального человека. Папка `media/` исключена из Git, чтобы не публиковать
эталонные фотографии пользователей.
Старые файлы `test-prisoner-*.jpg` — неиспользуемые заглушки; активные тестовые
карточки ссылаются на `public-portrait-01.jpg` ... `public-portrait-20.jpg`.

Фото карточек хранятся в `media/prisoners/reference/` и доступны контейнеру backend
через bind mount. Для уже созданных карточек, чьи фото ранее попали в S3, выполните
один раз перед перезапуском backend:

```bash
docker compose build backend
docker compose run --rm --no-deps backend python manage.py migrate_reference_photos
docker compose up -d backend
```

Команда копирует только фото карточек, не удаляя исходные объекты S3. Чтобы использовать
своё фото для биометрии, загрузите его в поле `photo` конкретной карточки осуждённого
через API `PATCH /api/prisoners/{id}/` (`multipart/form-data`); одного копирования файла
в папку недостаточно, если карточка ссылается на другое имя.

Локальная проверка без Docker:

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/python manage.py migrate
.venv/bin/pytest
cd frontend && pnpm install && pnpm build
```

Архитектурные решения и границы интеграции описаны в
[`docs/architecture.md`](docs/architecture.md).

Первая версия проекта будет предназначена для одной конкретной задачи - автоматизации заключения трудовых договоров. В рамках реализации данной задачи мы пока не рассматриваем перенос исторических данных, только свежий сценарий.

Система представляет собой заявочную систему с последующим заключением договоров.

Система включает в себя участие следующих лиц:
 - МСБ - бизнес, который хочет заключить договор с заключенными
 - РГП Енбек, который осуществляет управление и мониторинг заключенных
 - сами заключенные, которые должны будут ознакомиться с договором и подписать его

 Соответственно, для каждого из них предусмотрены свои личные кабинеты с определенным функционалом.

Сам бизнес процесс должен идти так:
1. МСБ заходит на сайт и регистрируется. На основании информации из презентации подготовь небольшой лендинг, базовые разделы - главная, о нас, преимущества, как это работает и т.д.

Также обязательно нужен раздел с указанием текущего кол-ва сотрудников-заключенных в системе. Мы не выводим их фото и прочую информацию в публичный доступ, только количественные выражения. Столько-то инженеров, столько-то электриков и т.д. Основная задача - дать понять сколько людей есть в системе.

Далее МСБ регистрируется, должен указать следующие данные:
 - название юр лица
 - БИН
 - вид деятельности
 - штат
 - юр адрес
 - факт адрес
 - галочка юр адрес совпадает с фактическим. Если тыкнул, то факт адрес можно не заполнять, подставляется с юр адреса и не редактируется
 - ОКЭД - нужен справочник
 - банковские реквизиты
 - наличие лицензий, разрешений, если есть
 - первый руководитель
  - ФИО
  - ИИН
  - Должность
  - Контактные данные - почта и номер телефона

  Создается профиль организации, карточка юр лица. Тот, кто регистрируется, является администратором организации. Он администрирует данную учетную запись.

  В личном кабинете он может видеть профиль компании, свои текущие заявки на работников и трудовые договора. В профиле можно редактировать только банковские реквизиты, данные первого руководителя и банковские реквизиты.

  Теперь он может подать заявку на работников, он делает это из раздела в личном кабинете. На лендинге можно добавить переход в этот раздел. 
  
  2. Подача и обработка заявки
  При подаче заявки он должен обязательно заполнить:
  - кол-во людей, которые ему нужны
  - специальность этих людей - из справочника - тут идет связка с навыками
  - только с навыками или берут для обучения - тут важный момент, может быть требование только с владением навыками. Тогда Енбек не может предложить людей без навыка. Если рассматривается возможность обучения, можно предлагать людей без навыков. Тут нужно или два параметра сделать галочками или еще как-то. Очень важно добавить описание параметров, чтобы пользователь понимал, если он нажмет галочку Только с навыками, то ему не смогут предложить людей без навыков. Если с обучением, то могут предлагать и таких и таких. Один из двух этих параметров, не оба разом.
  - место работы - указывает адрес, пока просто строкой
  - ЗП
  - длительность - на год - по умолчанию, без возможности редактировать
  - график - 5/2, с 9 до 5 и т.д. или другое значение, заполняет строкой
  - частичная или полная занятость - справочник
  - вид деятельности - также строка, что он будет делать с этими людьми

  Заявка формируется и отправляется в систему. Потом доступна в личном кабинете, где МСБ может посмотреть свою заявку. Может отозвать, отредактировать может только пока по ней не пришел ответ от РГП Енбек, удалить не может.
  
  Далее заявка попадает в РГП Енбек. Там она попадает к сотруднику. Сотрудник должен изучить эту заявку и дать ответ на нее. Внутри заявки система должна помочь сотруднику подобрать исполнителей. Ему выдается список с карточками заключенных, тут уже отображается вся полная информация, РПГ Енбек имеет к ней доступ. Там должны быть указаны навыки и прочее. А также рейтинг, т.к. у заключенных есть рейтинг риска, как-то так. Логика формирования этой оценки пока не ясна, поэтому пока ориентируемся на 5-ти звездочную систему. Чем выке рейтинг - тем выше кандидат в списке. На самом верху совпадения навык + хороший рейтинг, потом навык + слабый рейтинг, потом без навыка + хороший рейтинг, потом без навыка и без рейтинга и т.д. Фильтр по двум параметрам - рейтинг и навык

  Карточки можно отобразить в виде списка - тут на твое усмотрение, главное чтобы было удобно. Обязательно нужна фильтрация и поиск по параметрам. Также очень важный параметр тут будет - есть ли у этого заключенного другие активные договора.

  Сотрудник протыкивает галочками людей, которых он хочет предложить. Не более заявленного кол-ва. Если в заявке 10, может направить только 10. Может направить меньше, но не больше.

  Теперь ответ поступает в кабинет МСБ. Он может видеть кого направили ему в ответ. Может видеть только фото, навыки и рейтинг, без ФИО, без прочей информации. Если без навыка, так и пишется, без навыка. Он может протыкать галочками кого хочет, кого нет. Также может указать общий комментарий. Также МСБ может отклонить предложение полностью, не выбрав никого. Тогда заявка считается закрытой, фиксируется статус "Отклонено по инициативе заявителя". Ответ отправляется в Енбек.

  Теперь, если МСБ кого-то выбрал, сотрудник в Енбек получает ответ. Теперь он может согласовать, либо отклонить. Также указывает комментарий. Если отклоняет, то фиксируется статус "Отклонено по инициативе Енбек". Если согласует, МСБ приходит ответ. Заявка считается закрытой, она не редактируется. Но внутри нее, в рамках этой заявки, проходит дальнейшая работа. Следующий этап - Подготовка к обследованию.

  Нужны уведомления всем сторонам, о том, что произошло новое действие. Пока уведомления только внутри самой системы, без смс и писем, в дальнейшем возможно расширим.

  3. Прохождение мед комиссии и спец проверки
  Сотрудник переходит внутрь заявки, направляет людей на этап мед обследования. Он выбирает галочками кого направить и нажимает соответствующую кнопку. Люди, которых отобрали, далее попадают на этап обследования. По факту в системе в этот момент ничего не происходит. Направленные попадают в ЛК к медику. В своем ЛК медик видит только входящие заявки на обследование. Также он должен иметь возможность ознакомиться с информацией самой заявки, на случай, например, если подразумевается тяжелая работа, а заключенному по здоровью нельзя. Медик указывает комментарий и указывает заключение - две кнопки Согласовать и Отклонить. Указывается комментарий и там и там. Если отклонена, данный сотрудник-заключенный не идет далее по этапам, фиксируется отказ от медика.

  Далее сотрудник направляет тех, кто прошел этап мед проверки, у себя в ЛК направляет на спец проверку. Там принцип тот же, уже в ЛК сотрудника спец проверки.

  Те, кто проходят оба этапа, доходят до заключения договоров. Сотрудник также внутри заявки направляет на заключение договора. Только тех, кто проходит оба этапа.

  МСБ у себя в ЛК видит как идет обработка, кто дошел до какого этапа.

  4. Заключение трудовых договоров
  Теперь сотрудник приступает к созданию трудовых договоров. Это происходит на основании текущей заявки, это связь должна быть обязательно построена.

  Внутри заявки должна быть кнопка Создать трудовые договора. Система создает новые записи, которые в дальнейшем видны в разделе Трудовые договора
  Там фиксируется:
  - номер договора - формируется автоматически
  - дата начала действия договора
  - дата завершения договора
  - данные по юр лицу, с кем заключен договор
  - данные по физ лицу, заключенному, с кем заключен договор
  - статус - действующий или истекший, если договор уже подписан
  - статусы подписания - если договор еще не заключен, у него нет статуса Подписан, т.е. он не действующий. Сначала он должен быть подписан заключенным, он должен подписать первым, это обязательно. Далее подписывают Енбек и МСБ, в любом порядке. Как только подписали все, договор считается подписанным. По каждой подписи внутри должна быть дата подписи, т.е. дата движения договора далее по процессу
  - дата создания договора в системе
  - сам документ
  - на основании какой заявки был документ

  Документ формируется по шаблону, туда подставляются реквизиты Енбек, МСБ (которые он заполнил при регистрации). Договор новый, в первую очередь его должен подписать работник-заключенный.

  Кол-во договоров зависит от того, сколько людей было в заявке. Для каждого из них создается договор.

  В разделе Договора должен быть список, фильтры. 

  5. Подписание догоров

  Сотрудник-заключенный должен подписать договор. У него нет личного кабинета, т.к. нет компьютера и т.д. Это же заключенные все таки. Процесс идет так. Сотрудник в своем личном кабинете, в конкретном договоре выбирает опцию Подписать от заключенного (или как-то так, название рабочее). В этот момент заключенный должен присутствовать в комнате, подписание идет через биометрию. У меня есть biometry-service, описание есть в readme и в переписке в чате. Интегрируемся с ним, вся логика оттуда. Заключенный посмотрел в камеру, прошел биометрию, документ подписался. Обязательно нужно сохранять факт согласия, что это был действительно он, можно фотографии в этот момент сохранить. Сверка фото идет с фото заключенного в ЛК.

  Далее договор могут подписать ЕНБЕК и МСБ, в любом порядке, статусы идут соответствующие.

  Это уже финальный этап, по сути все.

  РГП Енбек - это организация. Там должны присутствовать такие роли:
  - администратор - управляет пользователями, системными справочниками и т.д.
  - руководитель - осуществляет управление процессом
  - исполнитель - основной работник
  - психолог - сотрудник, проводящий определенный этап обработки - псих обследование
  - специалист - сотрудник, проводящий определенный этап обработки - спец проверку

  Каждая из ролей отвечает за определенный этап бизнес процесса.

  Основой системы являются карточки заключенных, т.к. нужно вести учет их трудовых договоров и их работы. Далее, соответственно, трудовые договора.

  Пока нет конечной информации что должна включать в себя карточка заключенного
  Однозначно должна включать:
  - ФИО
  - ИИН
  - Дата рождения
  - Навыки - это один из ключевых параметров, т.к. по ним потом идет выборка для работы с МСБ. Слесарь, электрик и т.д.
  - фото

  Пока это вся нужная информация, можем назвать ее основой профиля. Данных будет больше, их распихаем по другим таблицам.

  Также есть трудовые договора. По ним соответственно:
  
  Нужно иметь возможность просматривать занятость, просматривать карточки и редактировать информацию при необходимости, просматривать информацию о трудовых договорах, обрабатывать заявки.

  Должен быть дашборд с отображением нужной инфы.

  Общие требования
